Basic Architecture (GameObjects and Components)

GameObjects

GameObjects:

GameObjects are the fundamental objects in Unity that represent characters, props, and scenery.

They do not accomplish much in themselves, but they act as containers for Components(Scripts), which implement the real functionality.

Base GameObject has name, tag, layer, and transform component

Scripts Are Components and define the empty GameObject

GameObjects and Components(Scripts) are Initialised and run when play is pressed

Scripts must be attached to a GameObject in order for scripts to run (more later).

Scripts can be attached to an Empty gameObject.

All GameObjects Components and Scripts in scene(s) in build

Are available to run if accessed and visible.

GameObjects will have variable and references that can be modified.

References can be to any Components, GameObjects, or Assets.

https://docs.unity3d.com/Manual/class-GameObject.html

Components:

Components are scripts, either pre-defined library or user defined

GameObjects will come with default Components(scripts) depending on

Type, and these define the blank GameObject.

The Transform Component is the basic GameObject Component,

Along with name, tag, and layer.

https://docs.unity3d.com/Manual/unity-components.html

Basic Architecture

MonoBehaviour, Scripts, Classes, Namespaces

Classes - Monobehaviour and Unity Structure:

MonoBehaviour is the base class for all scripts in the UnityEngine Namespace.

When using C#, you must explicitly derive from MonoBehaviour.

Classes are derived from the Script via MonoBehaviour, which Unity is built on.

NameSpaces:

Namespace: A logical container used to group related classes, structs, and enums so they don’t clash with other code.

Namespaces are used to organize classes and avoid naming conflicts.

MonoBehaviour is a class in the Namespace: UnityEngine.

For Example:

using UnityEngine;

using System.Collections;

Other namespaces may exist, but they do not define classes directly.

Others are not Class Definitions.

Dependencies:

Libraries of Classes provided by Unity, third parties, or yourself.

For Example:

using UnityEngine; is a code-level dependency that allows access to Unity's core classes and functions.

using System.Collections; is a code-level dependency that allows access to collection classes like ArrayList, Hashtable, etc.

Dependencies are important because they allow your scripts to access and use functionality provided by other libraries and frameworks.

With Dependencies, Unity provides a framework so that you don't have to work out input handling, graphics instance setup, game loop, game object handling, physics, rendering, lighting etc yourself.

Scripts:

Scripts are used to define the behavior of GameObjects in Unity.

They are written in C# and derive from the MonoBehaviour class.

Scripts contain methods(functions) like Start() and Update() that define the behavior of the GameObject they are attached to.

These methods are called by the Unity engine at specific points in the game loop.

Common methods include:

  • Start(): Called before the first frame update.
  • Update(): Called once per frame.
  • Awake(): Called when the script instance is being loaded.
  • OnDestroy(): Called when the MonoBehaviour will be destroyed.

These are some of the most commonly used methods in Unity scripts, but there are many others available depending on the specific needs of your game.

It's important to understand the lifecycle of these methods to effectively control the behavior of your GameObjects.

The Start() function will be run only once at the start of the program. So any logic and data initializations that you need or want to do can be placed in the Start() function.

The Update() function is where most of the magic happens. This is the function that gets called continuously throughout the life of your game or simulation. This is the function where you will update your game objects. In short it is the function which will be called each frame before rendering the scene.

Basic Architecture (Scenes, Views and Cameras)

Scene and Game Views

Scene View

The Scene view is the editor workspace where you build and inspect a scene.

You can move around the scene, select GameObjects, and use the Transform tools to position, rotate, and scale them.

The Scene view is an editor view; it is not necessarily what the player sees.

Game View

The Game view shows the scene from the active Camera while the project is running.

Main Camera and Lighting

Main Camera

A Camera defines a view into the scene. A basic scene needs a camera if you want to see the scene through the Game view.

The camera can be positioned and configured like other GameObjects through its Transform and Camera components.

Lighting

A new scene commonly includes a Directional Light. Lighting determines how visible surfaces appear in the rendered scene.

More advanced cameras and lighting approaches will be introduced later in the module.

Scene as a Working Unit

A useful mental model

A Scene is a collection of GameObjects.

GameObjects contain Components.

Components provide data and behaviour.

The Inspector is used to configure those objects and components.

The Camera provides a view of the scene when it runs.

Basic Architecture (Assets, Packages and Prefabs)

Assets and Packages

Assets

Assets are project resources such as models, textures, materials, audio, scripts, scenes and other data.

They can be created inside Unity or imported from external files.

Packages

Packages group related Unity or third-party functionality so that it can be added to a project as a unit.

The Package Manager is used to manage packages and their versions.

This modular approach lets a project use the functionality it needs without every project being structured identically.

Prefabs

Prefab as a reusable GameObject setup

A Prefab is a reusable asset that stores a GameObject and its configured components and child objects.

Prefabs are useful when the same object needs to appear repeatedly or needs to be instantiated at runtime.

Changing the Prefab can update its instances, subject to any instance-level overrides.

Prefab Instantiation

Editor and runtime use

A Prefab can be placed into a Scene in the editor, or instantiated by a script at runtime.

This separates the design of an object from the code that decides when and where it appears.

Example

An enemy, projectile, vehicle or repeated environmental object can be designed once as a Prefab and then reused many times.

Basic Architecture (Components and Controllers)

Components

GameObjects are built from Components

Components provide the data and behaviour attached to a GameObject.

The Transform component is fundamental because it describes position, rotation and scale.

Other common components include Mesh Renderer, Collider, Rigidbody, Camera, Light, Animator and user-created scripts.

Different GameObjects can therefore be assembled from different combinations of components.

Controllers

Behaviour can be provided by different controller systems

Scripts can implement custom behaviour and respond to input, physics, collisions, timers and other events.

Animator provides a visual system for controlling animation states and transitions.

Character and navigation systems can provide higher-level movement and animation behaviour.

These systems are components or packages that work within the wider GameObject and Component architecture.

Architecture in Practice

From object to behaviour

Choose or create a GameObject.

Add the Components required to describe it.

Configure those Components in the Inspector.

Add a script when custom behaviour is required.

This component-based approach is one of the central ideas students will use throughout the module.

Basic Architecture (Scripts and the Unity Lifecycle)

Scripts as Components

Scripts add behaviour

A C# script that derives from MonoBehaviour can be attached to a GameObject as a Component.

Its variables can expose data or references in the Inspector, while its methods define behaviour.

Unity calls specific lifecycle methods at appropriate points while the object is loaded and running.

Basic C# Script
Basic Unity C# Script
using UnityEngine;
public class ExampleBehaviour : MonoBehaviour {
void Start () {
// Initialisation happens here
}
void Update () {
// Per-frame behaviour happens here
}
}

What this shows

using UnityEngine; gives access to Unity's core classes.

MonoBehaviour makes the class usable as a Unity Component.

Start() is commonly used for initialisation.

Update() is called once per frame while the behaviour is enabled.

Lifecycle and Execution Order

Common methods

Awake() is used for initialisation when the script instance is loaded.

OnEnable() is called when the component becomes enabled.

Start() is called before the first frame update when the component is enabled.

Update() runs once per frame.

OnDestroy() is called when the object or component is destroyed.

Script execution order can be configured when a project requires particular scripts to run before others. Do not assume that unrelated scripts execute in the order they appear in the Project window.

Working in Unity (Editor, Toolbar and Play Mode)

Editor Workflow

Build, inspect, test, repeat

Unity is an interactive development environment as well as a runtime engine.

The main workflow is to create or import assets, assemble GameObjects in a Scene, configure Components in the Inspector, and then test the result in Play mode.

The Console is used to inspect errors, warnings and diagnostic messages.

Scene Toolbar and Transform Gizmos

Basic Scene controls

The Scene toolbar provides tools for selecting, moving, rotating and scaling objects.

Transform tools can work in local or global coordinates.

Pivot and centre modes affect where a transform operation is applied.

These controls are essential for positioning objects before scripting or runtime behaviour is introduced.

Play Mode

Testing the running scene

Play mode runs the current project using the Scene configuration.

Values can be changed during Play mode to experiment and debug.

Changes made to scene objects during Play mode are not normally retained when Play mode stops.

This makes Play mode a safe place to test behaviour without permanently changing the project.

Basic Architecture (Shading and Lighting)

Materials, Shaders and Rendering

How a surface becomes an image

A Mesh provides geometry. A Renderer uses that geometry with a Material to produce a visible surface.

A Material uses a Shader to determine how the surface is rendered, including properties such as colour, texture and response to light.

Lighting then affects how the material appears in the scene.

These ideas will be developed in more depth later in the module.

Skybox and Environment

Skybox

A Skybox provides an environmental background around the scene and can contribute to the visual sense of lighting and space.

It is configured through the scene's lighting/environment settings rather than being ordinary scene geometry.

Demo

Create or select a suitable Material and inspect its Shader settings. The exact workflow depends on the rendering pipeline used by the project.

Rendering Pipeline

Keep the concept simple for now

Unity projects use a rendering pipeline that determines how cameras, lights, materials and shaders are processed.

Students do not need to master the rendering pipeline in this lecture. The important idea is that visible results are produced by several connected systems rather than by a Mesh alone.

Unity (C#) Concepts: Classes, Namespaces and Dependencies

C# Classes in Unity

Classes

A class defines a type that can contain data and methods.

Unity uses classes extensively: GameObjects, Components and many systems are represented through classes in the Unity API.

A script such as ExampleBehaviour defines a class that derives from MonoBehaviour.

MonoBehaviour

MonoBehaviour is the Unity base class that allows a C# class to function as a component attached to a GameObject.

Namespaces

Organising code

A namespace groups related types and helps prevent naming conflicts.

UnityEngine is a namespace containing many of Unity's core classes.

The statement using UnityEngine; allows those types to be referred to without repeatedly writing the namespace.

Dependencies

Using existing frameworks

A dependency is functionality that your code relies on but does not implement itself.

Unity provides frameworks for areas such as scenes, GameObjects, components, rendering, physics and input.

This is one of the main reasons an engine can support rapid development: students can use established systems rather than implementing an entire runtime from scratch.

Unity (C#) Concepts: Unity Framework vs General C#

What Unity Adds to C#

C# is still C#

Unity uses C# as its scripting language, but scripts operate inside the Unity framework and lifecycle.

Unity provides APIs and systems for GameObjects, Components, scenes, rendering, physics, input and many other areas.

This means students are learning general programming concepts while also learning how those concepts are used within an engine.

Constructors and MonoBehaviour

Why Unity scripts use a different pattern

In general C#, constructors are commonly used to initialise objects when they are created.

MonoBehaviour components are created and managed by Unity, so students should not treat a MonoBehaviour constructor as the normal place for Unity component initialisation.

For this module, use Unity lifecycle methods such as Awake() and Start() for initialisation, as appropriate.

General Programming Still Matters

The computer science connection

Classes, objects, methods, variables, types, control flow, abstraction and data structures remain C# programming concepts.

Unity adds an application framework around those concepts rather than replacing them.

This distinction becomes increasingly important as projects become more complex.
