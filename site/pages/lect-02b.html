A Unity Script: Class, Component and Lifecycle

Read the structure before reading the instructions

Namespace access

using UnityEngine; makes UnityEngine types such as MonoBehaviour, GameObject, Transform, Renderer and Debug available without writing their full namespace every time.

Class and inheritance

PlayerBehaviour is a class. : MonoBehaviour means it inherits from Unity's MonoBehaviour class, allowing instances of the script to participate in Unity's Component and event lifecycle.

PlayerBehaviour.cs
using UnityEngine;
public class PlayerBehaviour : MonoBehaviour
{
void Start()
{
Debug.Log("PlayerBehaviour started");
}
void Update()
{
// Frame-by-frame behaviour goes here.
}
}

Unity creates and manages the Component

For normal MonoBehaviour scripts you do not write new PlayerBehaviour(). You attach the script to a GameObject and Unity manages the Component instance and calls recognised event methods.

Lifecycle: put code where it belongs

Awake()

Useful for early setup that belongs to this Component, particularly obtaining references that do not depend on other objects having completed Start().

Start()

Runs before the first frame update when the behaviour is enabled. It is a common place for one-off initialisation.

Update()

Runs once per rendered frame while the behaviour is enabled. It is appropriate for frame-based logic and, in the Legacy Input Manager, polling input.

Later lifecycle methods

Lecture 03 will use FixedUpdate() for Rigidbody physics and OnEnable()/OnDisable() when enabling and disabling New Input System actions.

Data in a Unity Script: Variables, Types and Inspector Fields

Variables describe state

Type → name → value

A variable gives data a name. Its type determines what kind of value can be stored and what operations make sense.

Common C# and Unity types
int score = 0;
float moveSpeed = 5f;
bool visible = true;
string playerName = "Player One";
Vector3 startPosition;
GameObject target;
Renderer objectRenderer;

Value types and references

Numbers and booleans directly represent values. Unity types such as GameObject and Renderer are commonly used as references to objects or Components that already exist in the Scene.

Choose a meaningful type

A movement speed is naturally a float; a yes/no state is a bool; a 3D position is a Vector3; a Renderer reference should be stored as Renderer.

Declaration, initialisation and assignment

The terminology

A variable normally moves through a small lifecycle of its own: it is declared, given a value, read, changed and assigned again. These terms describe different operations, even when several appear on one line.

Declaration and assignment — individual statements
int score; // Declare an int variable named score
score = 0; // Assign 0 to the existing variable
int lives = 3; // Declare and initialise in one statement
score = score + 1; // Read score, add 1, assign the result back
score++; // Increment score by one (short form)

The same operations in context

The statements become more useful when they are part of a complete behaviour. Here, score and lives are fields: they belong to each instance of the Component. Start() establishes initial state and Update() changes that state in response to events.

ScoreAndLivesExample.cs — variables changing at runtime
using UnityEngine;
public class ScoreAndLivesExample : MonoBehaviour
{
// Fields store state for this Component instance.
private int score; // Declared here; default int value is 0.
private int lives = 3; // Declared and initialised to 3.
void Start()
{
// Explicit assignment: give score its starting value.
score = 0;
Debug.Log("Starting score: " + score);
Debug.Log("Starting lives: " + lives);
}
void Update()
{
// A single press changes the stored score.
if (Input.GetKeyDown(KeyCode.Space))
{
score = score + 1; // Read, calculate, then assign.
// score++; // Equivalent short form for +1.
Debug.Log("Score is now: " + score);
}
// Example of changing a second variable.
if (Input.GetKeyDown(KeyCode.L))
{
lives--; // Subtract one from lives.
Debug.Log("Lives remaining: " + lives);
}
}
}

Trace the value

If score starts at 0, the first Space press reads 0, calculates 1, and stores 1. The next press reads 1, calculates 2, and stores 2. The variable therefore represents changing program state across frames.

Fields versus local variables

score and lives are declared at class level, so multiple methods can use them. A variable declared inside Start() or Update() is local to that method or block and cannot be used everywhere in the class.

Inspector exposure without making everything public
Serialized fields
[SerializeField] private float moveSpeed = 5f;
[SerializeField] private GameObject target;
private Renderer objectRenderer;

[SerializeField] private

This keeps the field private to the class while asking Unity to serialize and display it in the Inspector. It is a useful default for designer-adjustable values and drag-and-drop references.

public is an access modifier

A public field can also appear in the Inspector when Unity can serialize its type, but public primarily controls code access. It should not be taught as meaning 'show this in the Inspector'.

Expressions and Decisions: Turning Data into Behaviour

Expressions produce values

Arithmetic

Expressions such as score + 1, moveSpeed * 2f and distance / time calculate values that can be assigned or used by another expression.

Comparison

score >= 10, speed == 0f and target != null evaluate to a Boolean value: true or false.

Logical operators

&& means AND, || means OR, and ! means NOT. The Tutorial 01 visibility toggle used NOT to reverse a Boolean state.

Boolean toggle
objectRenderer.enabled = !objectRenderer.enabled;
if, else if and else
Choose behaviour from state
if (score >= 10)
{
Debug.Log("Target reached");
}
else if (score > 0)
{
Debug.Log("Keep going");
}
else
{
Debug.Log("No score yet");
}

Control flow

Only the first matching branch in this chain executes. Conditions therefore determine which statements are reached at runtime.

Unity consequence

The same structure can decide whether an object is visible, whether a character can move, whether an animation should play, or whether a counter should wrap to the beginning of an array.

Null checks protect references
Check before use
if (objectRenderer != null)
{
objectRenderer.enabled = visible;
}

Why

A reference variable can contain no object. Attempting to access a member through a null reference causes a NullReferenceException. The better long-term solution is usually to ensure required references are assigned correctly, but recognising null is fundamental.

A complete decision-making Component

A fuller example shows why fields, references and conditions are normally taught together. The script obtains its Renderer once, stores a Boolean state, and uses keyboard events to change that state.

VisibilityController.cs — state + decisions + Component reference
using UnityEngine;
public class VisibilityController : MonoBehaviour
{
// State that belongs to this Component.
private bool visible = true;
// Reference to another Component on the same GameObject.
private Renderer objectRenderer;
void Start()
{
objectRenderer = GetComponent<Renderer>();
objectRenderer.enabled = visible;
}
void Update()
{
// Toggle visibility once when Space is pressed.
if (Input.GetKeyDown(KeyCode.Space))
{
visible = !visible;
objectRenderer.enabled = visible;
}
// R restores a known state.
if (Input.GetKeyDown(KeyCode.R))
{
visible = true;
objectRenderer.enabled = visible;
}
}
}

Components, References, Properties and Methods

Get a Component once, then use the reference
Store a Renderer reference
private Renderer objectRenderer;
void Awake()
{
objectRenderer = GetComponent<Renderer>();
}

GetComponent<T>()

Searches the same GameObject for a Component of type T. Here, T is Renderer.

Why store the result

Once the script has the reference, later code can use it directly instead of repeatedly searching for the same Component.

Inspector references are another route

If the required object is somewhere else in the Scene, a serialized field can expose a reference slot that you populate by drag and drop.

Putting references and methods together

This example stores a reference to a target GameObject in the Inspector and obtains a Renderer from the current GameObject. It then separates repeated behaviour into named methods, making Update() easier to read.

TargetController.cs — Inspector reference + GetComponent + methods
using UnityEngine;
public class TargetController : MonoBehaviour
{
[SerializeField] private GameObject target;
private Renderer objectRenderer;
void Awake()
{
// Cache a Component reference once rather than finding it every frame.
objectRenderer = GetComponent<Renderer>();
}
void Update()
{
if (Input.GetKeyDown(KeyCode.H))
{
HideThisObject();
}
if (Input.GetKeyDown(KeyCode.T) && target != null)
{
target.SetActive(!target.activeSelf);
}
}
private void HideThisObject()
{
objectRenderer.enabled = false;
}
}
Dot notation: reach a member of an object
Properties, fields and methods
objectRenderer.enabled = false;
transform.position = Vector3.zero;
gameObject.SetActive(false);
transform.Rotate(0f, 30f * Time.deltaTime, 0f);

Property or field

The member on the right of the dot may expose data, such as enabled or position. Assignment changes that member where the API permits it.

Method call

Parentheses indicate a method call. Values inside the parentheses are arguments supplied to that method.

Read the API from left to right

Which object do I have? → which member am I accessing? → am I reading data, assigning data, or calling behaviour?

Write methods to name useful behaviour
Small methods
void HideObject()
{
objectRenderer.enabled = false;
}
void ShowObject()
{
objectRenderer.enabled = true;
}

Why methods help

A method groups statements into a named operation. This reduces repetition and lets the code communicate intent: HideObject() is easier to reason about than repeatedly copying the implementation.

Classes, Objects, Access and Encapsulation

OOP becomes concrete in Unity

Class

A class defines a type: the data it can store and the methods it can perform. Your C# script file normally contains a class with the same name as the file.

Object / instance

An object is a particular instance of a class. Two GameObjects can each have their own instance of the same script Component and therefore hold different field values.

Inheritance

PlayerBehaviour : MonoBehaviour is inheritance. PlayerBehaviour gains behaviour and API relationships from MonoBehaviour while adding its own fields and methods.

Composition

Unity relies heavily on composition: build a GameObject by combining Transform, Renderer, Collider, Rigidbody, Animator and your own script Components rather than creating one enormous inheritance hierarchy.

Access modifiers are not the same as scope
Access examples
public class PlayerBehaviour : MonoBehaviour
{
[SerializeField] private float moveSpeed = 5f;
public bool CanMove { get; private set; } = true;
private void StopMoving()
{
CanMove = false;
}
}

private

Accessible from within the declaring class. It does not mean 'local'. A private field can exist for the lifetime of the Component.

public

Accessible from other code where the containing type is accessible. It does not mean 'global'.

Local variable

A variable declared inside a method or block has local scope, for example Vector3 force declared inside FixedUpdate().

Encapsulation

Keeping implementation details private and exposing only what other code needs reduces accidental coupling and makes classes easier to change.

Abstraction and polymorphism — recognise, do not over-focus

Abstraction

You can call SetActive(), AddForce() or GetComponent() through a clear API without knowing Unity's internal implementation.

Polymorphism

Different concrete types can be handled through a common base type or interface. This becomes more important in larger projects; for now, recognise the term rather than designing around it.

Constructors: Normal C# versus Unity MonoBehaviour

A constructor creates and initialises a normal C# object
Plain C# class
public class PlayerData
{
public string playerName;
public int score;
public PlayerData(string name)
{
playerName = name;
score = 0;
}
}
PlayerData data = new PlayerData("Alex");

Constructor

The constructor has the same name as the class and no return type. new PlayerData(...) creates an instance and the constructor establishes its initial state.

Useful distinction

Not every C# class in a Unity project needs to be a MonoBehaviour. Plain C# classes are useful for data and logic that do not need to be attached to GameObjects.

A more complete plain C# example

A constructor is most useful when an object should not exist without valid starting data. This ordinary C# class requires a name and starting health when it is created; the constructor establishes that state immediately.

CharacterData.cs — ordinary C# constructor
public class CharacterData
{
public string Name { get; private set; }
public int Health { get; private set; }
// Constructor: same name as the class and no return type.
public CharacterData(string name, int startingHealth)
{
Name = name;
Health = startingHealth;
}
public void TakeDamage(int amount)
{
Health = Health - amount;
}
}
// Somewhere in ordinary C# code:
CharacterData playerData = new CharacterData("Player One", 100);
playerData.TakeDamage(10);
Do not construct MonoBehaviours with new
MonoBehaviour pattern
public class PlayerBehaviour : MonoBehaviour
{
private Renderer objectRenderer;
void Awake()
{
objectRenderer = GetComponent<Renderer>();
}
}

Unity owns Component creation

MonoBehaviour instances are Components managed by Unity. Add the script to a GameObject in the Editor, or add a Component through Unity's API; do not use new PlayerBehaviour().

Awake and Start are not constructors

They are Unity lifecycle event methods. They are often where MonoBehaviour setup happens, but they are called by Unity after the Component exists rather than constructing the C# object in the ordinary way.

Why learn both

Understanding the difference prevents a common mistake and makes it clearer that Unity scripting is C# used inside an engine-managed object and Component lifecycle.

Collections and Repetition: Preparing for the Gallery

Arrays hold several values of the same type
Gallery array
[SerializeField] private GameObject[] galleryObjects;
private int counter = 0;
GameObject firstObject = galleryObjects[0];

Array

GameObject[] means a collection of GameObject references. Unity can serialize the array so its elements can be assigned in the Inspector.

Indexes start at zero

The first element is index 0. For an array of length 4, valid indexes are 0, 1, 2 and 3. galleryObjects.Length reports the number of elements.

Counter

An integer counter can represent which gallery element is currently selected. The program changes the counter, then uses it as an index.

for loops apply one idea to many objects
Activate only the selected object
for (int i = 0; i < galleryObjects.Length; i++)
{
galleryObjects[i].SetActive(i == counter);
}

Initialisation

int i = 0 creates the loop counter at the first valid array index.

Condition

i < galleryObjects.Length keeps the loop inside the valid index range.

Iteration

i++ advances to the next index after each pass.

The useful expression

i == counter is true only for the selected element. SetActive() therefore activates one object and deactivates the rest without separate code for every gallery item.

Wrap the counter instead of leaving the array
Forward wrap
counter++;
if (counter >= galleryObjects.Length)
{
counter = 0;
}

Why

After the last element, the next increment would create an invalid index. Resetting to zero creates a circular gallery.

First Look at Input: From Key Press to State Change

From Tutorial 01: a key press changes behaviour

A familiar starting point

Tutorial 01 used the Legacy Input Manager to connect a physical key directly to behaviour. This is useful because the complete path is visible in one place: poll a key in Update(), test the returned Boolean, then change a Component or variable.

LogoToggle_Legacy.cs — discrete input
using UnityEngine;
public class LogoToggle_Legacy : MonoBehaviour
{
private Renderer logoRenderer;
void Start()
{
// Get the Renderer attached to this GameObject.
logoRenderer = GetComponent<Renderer>();
}
void Update()
{
// GetKeyDown is true only on the frame the key is pressed.
if (Input.GetKeyDown(KeyCode.Space))
{
logoRenderer.enabled = !logoRenderer.enabled;
}
}
}

Discrete versus continuous input

A toggle should normally happen once per press, so GetKeyDown() is appropriate. Character movement normally continues while a key is held, so the following examples use GetKey().

Arrow keys: Transform movement and rotation

Transform-based control

A Transform can be changed directly without a Rigidbody. In this teaching example Up/Down move along the object's local forward axis and Left/Right rotate around its Y axis. This makes the relationship between input and Transform behaviour explicit.

Arrows_TransformController_Legacy.cs
using UnityEngine;
public class Arrows_TransformController_Legacy : MonoBehaviour
{
[SerializeField] private float moveSpeed = 5f;
[SerializeField] private float rotationSpeed = 90f;
void Update()
{
// Start each frame with no requested movement or turn.
float moveInput = 0f;
float turnInput = 0f;
// Held keys produce continuous input values.
if (Input.GetKey(KeyCode.UpArrow))
moveInput = 1f;
if (Input.GetKey(KeyCode.DownArrow))
moveInput = -1f;
if (Input.GetKey(KeyCode.LeftArrow))
turnInput = -1f;
if (Input.GetKey(KeyCode.RightArrow))
turnInput = 1f;
// Translate along the object's local forward direction.
transform.Translate(
Vector3.forward * moveInput * moveSpeed * Time.deltaTime,
Space.Self
);
// Rotate around the local Y axis.
transform.Rotate(
0f,
turnInput * rotationSpeed * Time.deltaTime,
0f
);
}
}

Why Time.deltaTime appears here

Update() runs once per rendered frame. Multiplying a movement rate by Time.deltaTime converts a per-second speed into the amount to move during the current frame.

What students should trace

Arrow key → GetKey() → numeric input (-1, 0 or 1) → movement/rotation calculation → Transform changes → visible motion.

WASD: Rigidbody movement with forces

Physics-based control

A Rigidbody should normally be moved through the physics system rather than by directly changing its Transform. Here Update() reads W/A/S/D into two stored input values and FixedUpdate() converts them into a 3D force.

WASD_AddForce_PhysicsController_Legacy.cs
using UnityEngine;
public class WASD_AddForce_PhysicsController_Legacy : MonoBehaviour
{
[SerializeField] private float moveForce = 10f;
private Rigidbody rb;
private float horizontalInput;
private float verticalInput;
void Awake()
{
// Cache the Rigidbody attached to this GameObject.
rb = GetComponent<Rigidbody>();
}
void Update()
{
// Read keyboard state every rendered frame.
horizontalInput = 0f;
verticalInput = 0f;
if (Input.GetKey(KeyCode.A))
horizontalInput = -1f;
if (Input.GetKey(KeyCode.D))
horizontalInput = 1f;
if (Input.GetKey(KeyCode.S))
verticalInput = -1f;
if (Input.GetKey(KeyCode.W))
verticalInput = 1f;
}
void FixedUpdate()
{
// Convert 2D keyboard intent into movement on the X/Z ground plane.
Vector3 force = new Vector3(
horizontalInput,
0f,
verticalInput
);
// Force mode uses Unity's physics timestep; do not multiply by deltaTime.
rb.AddForce(force * moveForce);
}
}

Transform versus Rigidbody

The Transform example changes position/rotation directly. The Rigidbody example asks the physics engine to apply a force, so mass, drag, collisions and other physics properties can affect the result.

Tutorial 02 connection

These examples establish the two movement patterns used in Tutorial 02: Arrow keys controlling a Transform and WASD applying Rigidbody forces. Lecture 03 can then rebuild the same intentions using the New Input System rather than introducing movement and a new input architecture simultaneously.

Why Lecture 03 changes the input architecture

What the Legacy examples teach well

They make polling, conditions, held keys, one-frame presses, Transform movement and physics forces easy to see in ordinary C#.

What becomes awkward

Physical controls are hard-coded throughout the behaviour. Supporting alternative keys, a gamepad, rebinding or several control schemes makes the scripts increasingly coupled to specific devices.

The bridge

Lecture 03 will compare this model with direct New Input System device access and then Input Actions: physical controls → action → value/button state → script → behaviour. The movement concepts remain; the input layer changes.

Putting Lecture 02 Together

Read one script as a system
GalleryController_Legacy.cs — integrated example
using UnityEngine;
public class GalleryController_Legacy : MonoBehaviour
{
// Assign gallery objects in the Inspector.
[SerializeField] private GameObject[] galleryObjects;
// Index of the object currently being shown.
private int counter = 0;
void Start()
{
ShowCurrentObject();
}
void Update()
{
// Move forwards once per Right Arrow press.
if (Input.GetKeyDown(KeyCode.RightArrow))
{
counter++;
if (counter >= galleryObjects.Length)
counter = 0;
ShowCurrentObject();
}
// Move backwards once per Left Arrow press.
if (Input.GetKeyDown(KeyCode.LeftArrow))
{
counter--;
if (counter < 0)
counter = galleryObjects.Length - 1;
ShowCurrentObject();
}
}
private void ShowCurrentObject()
{
// Visit every array element.
for (int i = 0; i < galleryObjects.Length; i++)
{
// Only the object at the current index is active.
galleryObjects[i].SetActive(i == counter);
}
Debug.Log("Current gallery object: " + counter);
}
}

What this combines

A MonoBehaviour class, serialized array, private state, Start and Update, a key event, if statements, incrementing and bounds checking, a method call, a for loop, array indexing, a Boolean comparison and a Unity API method.

Read behaviour before syntax

Describe what the script does in ordinary language first. Then map each behaviour back to the C# and Unity API that implements it.

How to work with the tutorial

Investigate

Use the Unity Manual for concepts and the Scripting API for specific classes, properties and methods. Look up unfamiliar members such as GameObject.SetActive, Input.GetKeyDown and KeyCode.

Implement

Type the code yourself and keep the Console visible. Compilation errors are part of the programming workflow: read the first useful error, identify the file and line, and correct one problem at a time.

Test

Predict a result before entering Play Mode. Test boundary cases: first gallery object, last gallery object, repeated key presses and missing Inspector references.

Modify

Change one thing deliberately: use Left Arrow, reverse the gallery direction, alter an initial value, or add a Debug.Log showing the current counter.

Explain

Every student should be able to identify the data, condition, repetition and Unity API call responsible for the visible result. Programming should not be delegated to one member of a mixed group.
