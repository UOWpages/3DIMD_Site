5MMCS001W Lecture 03b — Input, Movement and Animation

From Lecture 02 state and behaviour to player control

Where Lecture 02 finished

We used the Legacy Input Manager to read keys and applied those values to simple Transform and Rigidbody movement. We already have the C# vocabulary: variables, references, methods, conditions, arrays, loops and lifecycle methods.

The question for Lecture 03

How should a Unity project represent player intent so the same behaviour can work with different controls, and how should that intent drive Transform movement, physics and animation?

Progression

Legacy Input Manager → direct New Input System device access → Input Actions → Vector2 movement → Transform controller → Rigidbody controller → movement state → Animator parameters.

Why compare old and new systems?

Old system as a readable baseline

The Legacy Input Manager makes the relationship between a key and a line of code very visible. That makes it useful for learning the basic idea of polling input.

New Input System as an abstraction

The New Input System separates the physical control from the action the game cares about. A script can ask for Move or Accelerate instead of hard-coding every keyboard or controller button.

Teaching goal

We are not learning two unrelated APIs. We are implementing the same behaviours twice so the architectural difference is visible.

Input Is Data: Events, State and Player Intent

Legacy Input Manager recap

Input changes while the program runs

A key can be treated as runtime data. The script reads that data and decides what behaviour should happen.

GetKeyDown versus GetKey

Input.GetKeyDown() is true only on the frame the key is pressed. Input.GetKey() remains true while the key is held. Choosing the wrong one changes the behaviour.

LegacyInputExample.cs
using UnityEngine;
public class LegacyInputExample : MonoBehaviour
{
void Update()
{
// A one-frame event: useful for toggles or discrete actions.
if (Input.GetKeyDown(KeyCode.Space))
{
Debug.Log("Space pressed");
}
// A continuous state: true while the key remains held.
if (Input.GetKey(KeyCode.W))
{
Debug.Log("Moving forwards");
}
}
}
Separate input from behaviour

Avoid thinking “W moves the player”

A better model is: the player expresses an intention to move forward; a control supplies that intention; the movement code interprets it.

Why this matters

Hard-coded keys are simple, but become awkward when controls change, when a gamepad is added, or when different players need different bindings.

Architecture we are moving toward

Physical control → Input binding → Action value → script → game behaviour.

New Input System: Direct Device Access Before Input Actions

The smallest conceptual step from the old system

Same idea, different API

Before introducing Input Actions, we can access the keyboard directly. This keeps the visible behaviour familiar while changing only the input API.

DirectKeyboard_NIS.cs
using UnityEngine;
using UnityEngine.InputSystem;
public class DirectKeyboard_NIS : MonoBehaviour
{
void Update()
{
// Check that a keyboard device is available.
if (Keyboard.current == null)
return;
if (Keyboard.current.spaceKey.wasPressedThisFrame)
{
Debug.Log("Space pressed with the New Input System");
}
if (Keyboard.current.wKey.isPressed)
{
Debug.Log("W is being held");
}
}
}
Read the expression from left to right

Keyboard.current

The current Keyboard device. Checking it for null prevents the script assuming that a keyboard is always available.

spaceKey and wKey

These identify physical controls on that device.

wasPressedThisFrame and isPressed

These correspond closely to the discrete and continuous ideas already seen with GetKeyDown and GetKey.

Limitation

This is still tied to a physical keyboard. Input Actions solve that by introducing a named action between the device and the script.

Input Actions: Describe What the Player Does, Not Which Key They Press

Create one PlayerControls Input Actions asset

Action Map: Player

An Action Map groups actions that belong to the same gameplay context. For these tutorials use a Player map.

Move actions

Create Player_WASD_Physics_AddForce_Move and Player_Arrows_Transform_Rotation_Move as Value / Vector2 actions. Each uses a 2D Vector Composite.

Button and look actions

Create Accelerate as a Button bound to Space. Create Look as Value / Vector2 bound to Mouse Delta. Look can exist now even if the first movement scripts do not use it.

2D Vector Composite turns four keys into one value

WASD

Up=W, Down=S, Left=A, Right=D. The action can produce values such as W=(0,1), S=(0,-1), A=(-1,0), D=(1,0). Diagonal combinations combine the axes.

Arrow keys

Use the same composite structure with Up, Down, Left and Right Arrow. Check the Right binding carefully: it should be Right Arrow, not Down Arrow.

Why Vector2?

The script receives one two-dimensional movement value instead of asking four separate questions about four keys.

Actions are the abstraction layer

Binding can change without rewriting movement code

A keyboard, gamepad stick or another suitable control can feed the same Move action. The movement script is concerned with the value, not the hardware that produced it.

Reading an Input Action from a MonoBehaviour

InputActionReference connects the Inspector to an action

A serialized private reference

[SerializeField] private InputActionReference moveAction; keeps the field private in C# while exposing an assignment slot in the Inspector.

Assign the action

Drag/select the appropriate Move action from PlayerControls.inputactions into the field on the Component.

ReadMoveAction.cs
using UnityEngine;
using UnityEngine.InputSystem;
public class ReadMoveAction : MonoBehaviour
{
[SerializeField]
private InputActionReference moveAction;
private void OnEnable()
{
moveAction.action.Enable();
}
private void OnDisable()
{
moveAction.action.Disable();
}
void Update()
{
Vector2 input = moveAction.action.ReadValue<Vector2>();
Debug.Log("Move: " + input);
}
}
Enable, read, disable

OnEnable()

Enable the referenced action when this behaviour becomes enabled.

ReadValue<Vector2>()

Read the current two-axis value. The generic type tells the Input System what value shape the script expects.

OnDisable()

Disable the action when the behaviour is disabled. This keeps the action lifecycle aligned with the Component lifecycle.

Do not rely on implicit enabling

An InputActionReference gives you a reference; explicitly enabling and disabling the action makes the script lifecycle clear.

Transform Movement: Arrow Keys as a Vector2 Action

Turn the action value into movement and rotation

One input value, two behaviours

The Y component of the Vector2 drives forward/back movement. The X component drives left/right rotation.

Arrows_transformRotation_CharController_NIS.cs
using UnityEngine;
using UnityEngine.InputSystem;
public class Arrows_transformRotation_CharController_NIS : MonoBehaviour
{
[SerializeField] private InputActionReference moveAction;
[SerializeField] private float moveSpeed = 5f;
[SerializeField] private float rotationSpeed = 90f;
private void OnEnable()
{
moveAction.action.Enable();
}
private void OnDisable()
{
moveAction.action.Disable();
}
void Update()
{
// x = left/right, y = forward/back from the Vector2 action.
Vector2 input = moveAction.action.ReadValue<Vector2>();
// Move along this object's local forward axis.
transform.Translate(
Vector3.forward * input.y * moveSpeed * Time.deltaTime,
Space.Self
);
// Rotate around the local Y axis.
transform.Rotate(
0f,
input.x * rotationSpeed * Time.deltaTime,
0f
);
}
}
Why Update() and Time.deltaTime?

Transform movement is frame-based here

This script directly changes the Transform rather than applying a physics force, so Update() is appropriate for this introductory controller.

Frame-rate independence

Multiplying speed by Time.deltaTime scales the amount moved or rotated by elapsed frame time. Without it, a higher frame rate would generally produce more movement per second.

Space.Self

The movement is relative to the object’s own orientation, so “forward” follows the direction the object is facing.

Physics Movement: WASD, Rigidbody and AddForce

Input becomes a force vector

2D input into a 3D world

The Input Action gives a Vector2. For movement across a ground plane, map input X to world X, input Y to world Z, and keep world Y at zero.

WASD_addForce_PhysicsController_NIS.cs
using UnityEngine;
using UnityEngine.InputSystem;
public class WASD_addForce_PhysicsController_NIS : MonoBehaviour
{
[SerializeField] private InputActionReference moveAction;
[SerializeField] private float moveForce = 10f;
private Rigidbody rb;
private Vector2 moveInput;
private void Awake()
{
rb = GetComponent<Rigidbody>();
}
private void OnEnable()
{
moveAction.action.Enable();
}
private void OnDisable()
{
moveAction.action.Disable();
}
void Update()
{
// Read player intent during the frame.
moveInput = moveAction.action.ReadValue<Vector2>();
}
void FixedUpdate()
{
// Map Vector2 x/y onto Unity world X/Z.
Vector3 force = new Vector3(moveInput.x, 0f, moveInput.y);
// AddForce participates in the physics simulation.
rb.AddForce(force * moveForce);
}
}
Update() and FixedUpdate() have different jobs

Update reads frame-based input

Store the current action value in moveInput. This keeps input sampling separate from the physics step.

FixedUpdate applies physics

Rigidbody forces belong in the fixed physics loop. AddForce() changes motion through the physics system rather than teleporting the Transform.

Do not multiply normal AddForce by Time.deltaTime

With the normal Force mode, Unity’s physics integration already accounts for the fixed timestep. Multiplying the force by Time.deltaTime would incorrectly scale the force again.

Rigidbody setup

Use Gravity on, Is Kinematic off. Interpolate can smooth visible motion. Freezing X/Z rotation can be useful for an upright character, depending on the exercise.

Transform versus Rigidbody: Choose the Movement Model Deliberately

Two controllers, two different models

Transform controller

Directly changes position/rotation. It is simple and predictable, but does not ask the physics engine to calculate the movement.

Rigidbody controller

Applies forces to a physics body. Mass, drag/damping, collisions and other forces can affect the result.

Do not mix them casually

Directly changing the Transform of a dynamic Rigidbody can fight the physics simulation. Decide whether physics should own the motion.

Debug the data path

1. Is the action producing a value?

Log the Vector2 before debugging movement. If it remains (0,0), inspect the action, binding, reference and enable state.

2. Is the value mapped correctly?

Remember that Vector2 uses x/y while ground-plane Vector3 movement usually uses x/z.

3. Is the correct system changing the object?

For Transform movement inspect Transform values. For physics inspect the Rigidbody, constraints, mass and collisions.

4. Is the script on the intended GameObject?

A correct script attached to the wrong object is still the wrong runtime configuration.

From Movement State to Animation

Animation should respond to state, not directly to a key

The useful question is “is the character moving?”

If animation is tied directly to W, it may fail for arrow keys, gamepads or movement generated another way. A movement state is a better abstraction.

MovementAnimation_NIS.cs
using UnityEngine;
using UnityEngine.InputSystem;
public class MovementAnimation_NIS : MonoBehaviour
{
[SerializeField] private InputActionReference moveAction;
[SerializeField] private Animator animator;
private void OnEnable()
{
moveAction.action.Enable();
}
private void OnDisable()
{
moveAction.action.Disable();
}
void Update()
{
Vector2 input = moveAction.action.ReadValue<Vector2>();
// sqrMagnitude is enough when we only need to know
// whether there is meaningful movement input.
bool isMoving = input.sqrMagnitude > 0.01f;
animator.SetBool("isMoving", isMoving);
}
}
Animator parameters connect code to transitions

Animator reference

Assign an Animator Component in the Inspector, or obtain it with GetComponent<Animator>() when appropriate.

Boolean parameter

Create an Animator parameter named isMoving. The script updates it with Animator.SetBool().

Transitions

Animator transitions can use isMoving == true to enter movement and isMoving == false to return to idle.

Data path

Input Action → Vector2 → Boolean movement state → Animator parameter → Animator transition → visible animation.

Putting the Data Path Together: Input → Movement → Animation

A complete Transform controller with animation state

Trace the script in stages

First obtain the input value. Second turn that value into movement and rotation. Third derive a Boolean state from the same value. Fourth send that state to the Animator.

PlayerTransformAndAnimation_NIS.cs
using UnityEngine;
using UnityEngine.InputSystem;
public class PlayerTransformAndAnimation_NIS : MonoBehaviour
{
[SerializeField] private InputActionReference moveAction;
[SerializeField] private Animator animator;
[SerializeField] private float moveSpeed = 4f;
[SerializeField] private float rotationSpeed = 120f;
private void OnEnable()
{
moveAction.action.Enable();
}
private void OnDisable()
{
moveAction.action.Disable();
}
void Update()
{
Vector2 input = moveAction.action.ReadValue<Vector2>();
transform.Translate(
Vector3.forward * input.y * moveSpeed * Time.deltaTime,
Space.Self
);
transform.Rotate(
0f,
input.x * rotationSpeed * Time.deltaTime,
0f
);
bool isMoving = input.sqrMagnitude > 0.01f;
animator.SetBool("isMoving", isMoving);
}
}
What this script demonstrates

Separation without unnecessary complexity

The script still fits on one page, but the data path is explicit: the input action supplies intent, the Transform code applies behaviour, and the Animator receives state.

Inspector configuration matters

The script requires a Move InputActionReference and Animator reference. Code and Editor configuration form one working system.

Test systematically

Test no input, forward/back, left/right, diagonals, enable/disable, and the Animator transitions. Predict what should happen before pressing Play.

Where This Leads: Actions, Events and Unity UI

The same architecture appears elsewhere in Unity

Input Action

Physical control → binding → named action → script method/behaviour.

Unity UI

Button or other UI control → event → method → behaviour.

Animator

Runtime state → parameter → transition → animation state.

Common idea

These systems reduce direct coupling. One part produces an event or value; another part responds to it.

What to take into Tutorial 02/03

Build both movement examples

Use Arrow keys for Transform translation/rotation and WASD for Rigidbody force so you can compare the two movement models.

Keep the old version

Do not overwrite the Legacy Input Manager version. Keeping old and new implementations side-by-side makes the migration visible and gives you a working comparison when debugging.

Everyone writes the core code

Mixed groups can discuss and troubleshoot together, but each student should be able to build, run, modify and explain the basic controller.

Next conceptual step

Later work can extend the same actions to gamepads, mouse look, UI and XR rather than replacing the architecture again.
