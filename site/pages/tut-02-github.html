4. Git Workflow: Modify, Stage, Commit and Push

Workflow

Visual Studio provides a menu on the top bar called Git and a right-side panel with Solution Explorer and Git Changes tabs. These are used to manage Git versioning on your local hard drive and the remote repository on the GitHub website.

You can create a repository from a local Unity Project, or clone one already on the GitHub website when you are logged in.

From here you can check which files are modified, stage changes, commit a local version update, and push or publish that update to the remote GitHub repository.

Fetch checks the remote for commits without changing your working files. Pull incorporates remote changes into your current local branch. Push sends your local commits to the remote. For this tutorial, use the explicit Pull and Push commands so the direction of each operation remains clear.

Actions

Microsoft Learn — Make a Git commit in Visual Studio

  1. Modified Files
    1. Seen in the Git Changes sidebar.
  2. Staged Files / Staged Changes
    1. Select individually with + next to each file in the Git Changes sidebar.
    2. Select all with + at the top of the Changes section.
  3. Commits
    1. Add a title/comments.
    2. You can choose to amend the previous commit or create a new one.
    3. You can choose Commit, or Commit and Push.
    4. Do not tick the “Amend” box!
  4. Push (Publish)
    1. Sends the local commit to remote/origin, if configured this way.
    2. Microsoft Learn — Push to a remote.
    3. [SIMPLE] How to push Visual Studio Project to GitHub.
  5. Fetch, Pull and Push
    1. Fetch checks for remote commits without merging them into your current branch.
    2. Pull incorporates remote changes into your current local branch.
    3. Before pushing collaborative work, check for incoming changes and Pull when required.
    4. Push sends your committed local changes to the remote repository.
    5. Microsoft Learn — Fetch, Pull and Sync.
  6. Stashing
    1. This allows you to stash your own changes temporarily, pull down group changes, then re-stage yours: source link.
    2. Right-click on stashes to re-apply or pop. Pop removes the stash after re-applying; Apply preserves it: source link.
  7. Working on the project in Github Browser with Copilot rather than locally will generate a PR, or pull request, which may make it harder to manage and merge unless you are used to this way of working.
Basic Git Cycle
Modify files
> Stage changes
> Commit locally
> Fetch / Pull remote changes when required
> Push to remote/origin

6. GitHub Group Work: Repository and Collaborators

Group repository

  1. Each group member should use their own GitHub account. Create one shared repository and grant access through collaborators or a GitHub Organization/Team; do not share a GitHub password.
  2. Separate student accounts can access a public repository and make changes.
  3. After the original GitHub repository is uploaded, it will look similar to the placeholder below.

Change visibility if needed to “public”

  1. On GitHub.com, navigate to the main page of the repository.
  2. Under the repository name, click Settings. If you cannot see the Settings tab, use the dropdown menu and then click Settings.
  3. Scroll to the bottom to see the Danger Zone.
  4. Click change visibility to make it public.

Add collaborators

  1. To Add Collaborators from the Group Github.com account, Invite the other members to collaborate:
  2. Ask for the username of the person you are inviting. If they do not have a username yet, they can sign up for GitHub.
  3. Navigate to the main page of the group repository.
  4. Click Settings.
  5. If you have an Organisation:
    1. Click Collaborators and Teams.
    2. Click Add People or Add Teams.
  6. If you do not have an organisation:
    1. Click Collaborators.
    2. Click Add People.
  1. In the search field, start typing the name of the person you want to invite, then select a name from the matches.
  2. Click Add NAME to REPOSITORY.
  3. The user receives an email invitation. Once accepted, they have collaborator access.
  4. Send each member the URL to the GitHub repository if they do not already have it.

8. Join an Existing Unity Project Repository

Clone the repository

Whether using collaborators or Teams, each individual group member clones the repository to their PC or laptop to work on it.

  1. This creates a version on your desktop and allows you to open the project in Unity and Visual Studio, and commit changes to GitHub using Visual Studio.
  2. After you are added as a collaborator, select the Git menu and Clone Repository.
  3. Give it a local path that is NOT the H: Drive, your student network drive, or an attached USB drive. The source document specifies C:Temp at University.
  4. Once the repository is cloned, open Unity Hub, navigate to the project location on your machine, and open the project/repository in Unity.
  5. Work with the project as normal, using Visual Studio for scripting.
  6. Commit changes to the local repository/project using Visual Studio Git: stage, commit staged changes, and push to the remote repository. Agree on a naming convention to track group-member contributions and versions.
  1. When you have changes that should be on the group repository at GitHub.com, select Push to Origin.
  1. The source document recommends having one person coordinate versions and contributions, including naming versions, contributors, and when to push to the origin repository.
  2. To inspect versions in Visual Studio 2026, open View > Git Repository (or use Git > View Branch History). GitHub.com can also be used to inspect the repository commit history.
  3. The Git Repository / branch history view shows commits and allows you to inspect the files changed by each commit.
  4. For normal student work, stay on a branch and inspect earlier commits rather than casually checking out old commits. If you need to restore work, first identify the required commit in the Git history and use an appropriate Git operation such as revert or create a branch from that commit.
